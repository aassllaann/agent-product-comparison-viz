### 🌟 论文整体特色与创新点（写作主线）

> **贯穿全文的四大创新亮点**：
> 1. **分层路由架构设计**：采用路由基座（`MultiCategoryAgent`）+ 品类专家代理（`CameraAgent`、`PhoneAgent`等10大原生品类）+ 动态拓展代理（`DynamicAgent`）的三级架构，支持未知品类的零配置动态生成评分体系。
> 2. **"AI意图解析 → 数据库精确检索 → LLM生成理由"的防幻觉闭环**：并非纯LLM对话，而是 LLM结构化提取（Slot Filling）+ SQLAlchemy精确过滤 + LLM生成推荐摘要的三段式设计，从根本上杜绝AI幻觉。
> 3. **可解释AI（Explainable AI）人机交互创新**：基于SOFT POP / MACARON主题设计系统，配合多维极坐标雷达图（Radar Chart）与分组柱状对比图（Grouped Bar Chart），将"黑盒"推荐透明化为可量化的多维能力图谱。
> 4. **全场景跨品类生态推荐（Eco-system Recommendation）**：通过语义得分匹配六大消费生态（移动办公、移动娱乐、专业游戏、摄影创作、音频发烧、健康运动），在主推荐链完成后自动延伸衍生品类推荐，实现"一个需求，全套解决"。

## 第一章 绪论

> **定位**：宏观破题，以用户痛点切入，简述现有研究不足，引出本文工作。**不分节，整体控制在1500～2000字（约1.5-2页）**，点到为止，不展开技术细节。

### 写作提纲与段落逻辑

**【第一段：背景与痛点】**

描绘电商平台的商品信息爆炸现象。据本研究问卷调查（n=20）显示，65%的用户在购买数码产品时需要一周以上时间做决策；超过70%的用户反映无法看懂专业参数；80%的用户认为当前测评主观性强，难以判断真实优缺点；85%的用户表示信息分散、需手动跨平台汇总。这一系列数字共同指向同一个核心矛盾：**信息越来越多，决策越来越难**。

**【第二段：现有研究的不足】**

简要说明三类现有方案均无法根本性解决上述问题：

- 传统协同过滤推荐系统依赖历史行为数据，缺乏对用户当下即时意图的理解能力，且存在严重的冷启动问题；
- 纯大语言模型对话推荐（如直接使用ChatGPT）虽具备自然语言理解能力，但易产生幻觉（虚构产品参数或不存在的型号），推荐理由缺乏可核实的事实依据；
- 内容型测评平台信息丰富但高度依赖创作者主观视角，用户仍需自行阅读大量内容后归纳，决策门槛未能实质降低。

三者均缺乏"即时意图理解 + 客观数据支撑 + 可视化辅助决策"的统一能力。

**【第三段：本文工作】**

在上述背景下，本文提出并实现了一套**基于多Agent架构的智能商品选购推荐系统**，核心思路是将大语言模型的语义理解能力与结构化商品数据库的事实约束能力相结合，通过三级Agent路由架构完成从自然语言输入到可视化推荐输出的完整链路。系统支持10大数码品类的精准推荐与未知品类的动态扩展，并通过多维雷达图与分组柱状图将推荐依据透明化呈现，有效降低用户决策门槛。

**【第四段：各章概述】**

最后一段简洁概述第二章至第七章的安排：第二章综述推荐系统、多Agent技术与可解释AI人机交互的相关研究；第三章基于问卷调研进行需求分析，并建立包含数据采集的系统总体框架；第四章重点阐述双层推荐引擎、多维打分与生态推荐等核心算法；第五章展示系统的工程实现细节；第六章通过功能测试与用户评估完成系统验证；第七章总结全文并展望未来改进方向。

## 第二章 相关工作

> **定位**：学术综述，为后续设计提供理论依据。控制在4000～5000字，每节引用不少于5篇文献。

### 第一节 推荐系统研究现状

**【1.1 传统推荐算法的原理与局限】**

系统梳理推荐系统三大技术流派：

**协同过滤（Collaborative Filtering，CF）** 分为基于用户（User-Based）和基于物品（Item-Based）两类，核心思路是"相似用户喜欢相似物品"。代表工作包括矩阵分解（Matrix Factorization）、SVD++ 等。其根本局限在于：依赖稠密的历史交互数据，存在严重的冷启动问题，且无法捕捉用户当前会话中的即时意图变化——"我要给孩子买教育用机"与"我要买游戏本"在行为数据上可能完全相同，但需求截然不同。

**基于内容的过滤（Content-Based Filtering）** 根据物品属性特征与用户历史偏好进行匹配，无需依赖群体数据，但局限在于特征工程繁琐、推荐结果趋于同质化（过滤气泡问题），且无法理解用户以自然语言表达的隐式偏好。

**基于知识的推荐（Knowledge-Based Recommendation）** 通过显式规则或领域知识图谱约束推荐范围，擅长处理高价值、低频次的决策场景（如数码产品选购），但规则构建成本高，难以实现自然语言交互，系统扩展性差。

**【1.2 基于大语言模型的推荐研究进展】**

近年来，以GPT、LLaMA为代表的大语言模型（LLM）被引入推荐系统领域，带来了显著的能力提升。TALLRec、LLM4Rec等工作提出将LLM作为推荐系统的核心推理引擎，利用其强大的语义理解能力将模糊的自然语言需求映射为结构化查询条件，有效突破了传统系统依赖关键词匹配的局限，并在一定程度上缓解了冷启动问题。

然而，纯LLM推荐系统存在明显的**幻觉风险（Hallucination）**——模型可能虚构产品参数或推荐实际不存在的商品型号。此外，推荐依据的透明度不足，用户无法验证推荐理由的真实性，这构成了LLM推荐系统在高决策风险场景（如数百元至数万元数码产品购买）中落地的核心障碍。

**【1.3 现有研究的空白】**

综合来看，现有推荐研究在以下三个维度存在明显不足：缺乏细分场景化（专家知识预置）的支持；缺乏跨品类统一路由框架；以及缺少基于真实结构化数据的幻觉抑制机制。本文正是在上述空白处着力设计。

### 第二节 多Agent系统研究

**【2.1 Agent的基本概念与理论基础】**

介绍Agent的经典定义：具备感知环境、自主决策和执行行动能力的软件实体（Russell & Norvig, 2020）。重点讲解Agent的三大核心要素：感知（Perception）、推理（Reasoning）和执行（Action），并区分反应式Agent（Reactive Agent）与慎思式Agent（Deliberative Agent）的设计差异。

**【2.2 多Agent系统的分布协作机制】**

说明多Agent系统（MAS）相对于单一Agent的优势：通过任务分解与职责分工，提升系统的可扩展性和容错性。重点介绍以下协作模式：

- **层级路由模式（Hierarchical Routing）**：中央协调Agent负责任务分发，子Agent专注细分领域执行。这与本文的 `MultiCategoryAgent` + 品类专家Agent的设计高度契合。
- **基于LangChain/LangGraph的路由与规划执行**：介绍业界主流的多Agent编排框架，以及其Router Chain、Tool Use等机制对本文架构设计的启发。

**【2.3 多Agent架构在推荐系统中的应用潜力】**

梳理近年来多Agent与推荐系统结合的研究进展：Agent通过多轮对话精炼用户需求（Conversational Recommendation）；多个领域专家Agent协作完成跨领域推荐任务；Agent的工具调用（Tool Use）能力使其可以实时查询外部数据库，突破LLM知识时效性限制。Park等人提出的生成式Agent框架（Generative Agents, UIST 2023）与MetaGPT的多Agent协作框架（Hong et al., 2023）均为本文架构设计提供了重要参考。

### 第三节 可视化辅助的LLM人机交互与可解释AI

> **写作重点**：本节聚焦"通过可视化手段支持大语言模型对话、增强AI决策可解释性"的学术研究，不涉及具体图表工具。重点引用CHI、IUI、UIST等人机交互顶会成果。

**【3.1 "黑盒"AI的信任危机与可解释性研究的兴起】**

深度学习时代的核心矛盾在于：模型能力越强，其决策过程越不透明，用户信任度越低。Ribeiro等人（KDD 2016）提出的LIME框架最早系统性地将"可解释性"作为AI系统的一等公民设计目标，指出用户对模型预测的信任建立在能够理解"为何做出此决策"的基础之上。此后，Lundberg & Lee（NeurIPS 2017）提出的SHAP方法将Shapley值引入特征重要性解释，成为可解释AI（XAI）领域的里程碑工作。

在人机交互领域，Liao等人（CHI 2020）通过用户研究系统梳理了用户对AI决策解释的需求类型，提出了"可解释性需求问卷（Explainability Needs Questionnaire）"，指出用户在高风险决策场景（如产品购买、医疗诊断）中对解释的渴求程度显著高于低风险场景。Wang等人（IUI 2021）进一步通过对照实验证明，提供决策解释的AI系统相较于"黑盒"系统，能显著提升用户的信任度与决策质量。这为本文将推荐理由可视化呈现的设计选择提供了坚实的学术依据。

**【3.2 思维链可视化与对话过程的透明化支持】**

随着大语言模型的广泛应用，如何将LLM的推理过程以用户可理解的方式呈现，成为人机交互研究的新兴热点。

Wei等人（NeurIPS 2022）提出的**思维链提示（Chain-of-Thought Prompting, CoT）**方法揭示了LLM的逐步推理能力，启发了后续一系列将LLM推理链路可视化的研究工作。Strobelt等人在CHI 2023提出了面向LLM对话的交互式推理路径展示系统，允许用户在对话界面中"打开"模型的中间推理步骤，显著提升了用户对AI回答的理解深度与信任感。类似地，Shen等人（IUI 2023）针对AI写作辅助场景，设计了将语言模型决策依据以高亮标注形式嵌入对话界面的交互方案，用户研究表明该方法能有效降低用户对AI建议的认知负担。

上述研究共同指向一个核心结论：**在LLM对话系统中，将推理过程与中间决策依据以结构化、可交互的形式呈现给用户，是提升系统可解释性与用户信任的有效途径**。本文在此基础上，将LLM的意图解析过程（槽位填充结果）与多维打分依据在推荐界面中透明化呈现，正是对上述研究结论的工程落地实践。

**【3.3 对话式AI中的渐进式信息披露与多维对比呈现】**

在复杂决策场景的对话系统设计中，如何在不造成信息过载的前提下呈现充分的决策依据，是HCI研究的长期课题。

Amershi等人（CHI 2019）在微软AI交互设计准则（Guidelines for Human-AI Interaction）中明确提出"渐进式信息披露（Progressive Disclosure）"原则：系统应优先呈现最关键的摘要性信息，并允许用户按需钻取更深层的细节依据。Cai等人（CHI 2019）通过医疗AI辅助诊断场景的研究发现，将AI置信度与关键特征权重以结构化方式呈现，比单纯给出结论的系统显著提升了医生的决策准确率与对AI的信任度。

在多备选项的对比决策场景中，Cheng等人（CHI 2019）研究了不同解释策略对非专业用户决策行为的影响，指出**多维度并排对比呈现（Multi-dimensional Side-by-Side Comparison）**比单独逐项描述更能帮助用户快速感知备选项之间的差异，并降低"选择困难"带来的认知疲劳。这一研究结论直接支撑了本文在推荐结果展示中采用多维雷达图与分组柱状图进行并排对比的设计决策——多维可视化并非单纯的美观追求，而是有学术实证支撑的认知辅助手段。

**【3.4 LLM生成解释的质量与用户感知研究】**

近年来，直接利用LLM生成自然语言形式的推荐理由，成为可解释推荐系统的重要研究方向。Li等人（2021）在可解释推荐系统综述中指出，自然语言形式的解释相较于特征权重列表，在用户主观理解度和接受度上具有显著优势，但同时存在生成内容可信度难以保障的问题。

这一发现揭示了纯LLM生成解释的根本局限：如果解释本身是基于幻觉生成的，再流畅的文字也无法建立真实的用户信任。Ye等人（ACL 2023）提出将检索到的真实事实与LLM生成的自然语言解释相结合的混合解释框架，有效提升了解释内容的事实可靠性。本文的设计与此高度契合：**LLM仅负责基于真实数据库检索结果生成自然语言摘要，事实判断由数据库精确查询完成**，从而在保持解释流畅性的同时，确保解释内容的事实可信度。

### 第四节 本章小结

归纳三节综述的核心发现，提炼现有研究在以下三个维度的不足，并说明本文如何针对性填补：

| 现有研究不足 | 本文解决思路 |
|---|---|
| LLM推荐易产生幻觉，缺乏事实约束 | 结构化数据库检索 + LLM语言生成的防幻觉双轨设计 |

| LLM对话中推理过程不透明，用户信任度低 | 意图解析过程展示 + 多维打分可视化 + LLM事实驱动解释生成 |

## 第三章 需求分析与方法设计

> **定位**：从"用户需要什么"推导出"系统应该怎样设计"，流程图须将数据采集环节包含在内，形成完整的通用处理流程。控制在3500～4500字。

### 第一节 需求层面分析

**【1.1 用户调研设计与执行】**

说明问卷设计思路：面向18-40岁有过数码产品购买经历的用户群体，通过线上问卷平台发放，共回收有效问卷20份。问卷分为三个模块：选购痛点识别、功能需求偏好、交互方式偏好。

**【1.2 痛点量化分析（配饼图与柱状图）】**

以下为核心痛点数据汇总（写作时配合图表呈现）：

| 痛点描述 | 比例 |
|---|---|
| 信息分散，需手动跨平台汇总比对 | 85% |
| 测评内容主观性强，难以判断客观优劣 | 80% |
| 专业参数难以理解（如光圈、TDP功耗） | 70% |
| 推荐理由不透明，不知为何被推荐某款 | 75% |
| 缺乏直观的横向对比图表辅助决策 | 40% |

> **写作技巧**：配一张水平条形图直观呈现以上数据，并附简要文字分析，说明"推荐透明度不足"与"参数壁垒"是用户反映最集中的两大核心痛点。

**【1.3 核心功能需求推导】**

基于痛点数据，按输入→处理→输出三层逐一推导系统功能需求：

- **输入层需求**：30%用户希望用简短口语直接表达需求（如"3000元拍视频的相机"），因此系统必须支持不规范的自然语言输入，无需用户填写结构化表单。
- **处理层需求**：65%用户希望每次获得3-5款精选推荐；80%用户需要了解推荐理由。系统须同时实现精准筛选与理由生成的双重能力。
- **输出层需求**：超过60%用户认为图表辅助能显著降低参数理解门槛，系统需提供具备多产品横向对比能力的参数可视化图表。

**【1.4 非功能性约束目标】**

- **通用性**：架构需支持10大核心品类，且具备新品类的无缝动态扩展能力。
- **客观性**：推荐过程必须以真实数据库记录为依据，杜绝LLM凭空生成产品信息。
- **响应性**：正常网络环境下，完整推荐结果（含图表渲染）的端到端响应时长控制在15秒以内。
- **可维护性**：遵循高内聚低耦合原则，新增品类只需新增一个派生Agent类，无需修改核心路由逻辑。

```
└─────────────────────────────────────────────┘
```

**【2.2 各层次模块职责划分】**

系统采用四层清晰分离的架构设计：

**① 事实数据层（Fact Data Layer）**
基于PostgreSQL + SQLAlchemy ORM，提供经清洗的10大品类结构化商品数据，确保所有推荐候选项均有真实数据支撑。该层在系统上线前通过ETL流水线完成数据准备，运行时对上层只读暴露ORM查询接口。

**② 业务决策层（Business Logic Layer）**
系统的核心大脑。维护各品类的异构评分基准，执行"Golden Sets场景匹配 → 价格过滤 → Fallback补库"的有序降级决策，并调用打分算法生成最终推荐榜单。

**③ 路由交互层（Intent Routing Layer）**
负责将用户原始输入通过大模型提示词工程（Prompt Engineering）进行槽位填充（Slot Filling），提取关键意图字段；并由 `CategoryDetector` 的双路检测机制（先关键词快速匹配，未命中时回退至LLM语义识别）将请求路由至对应专家Agent。

**④ 表象展示层（UI/Charts Layer）**
基于Streamlit构建单页状态应用，负责接收用户会话输入、维护 `st.session_state` 对话历史，动态渲染商品卡片、雷达图、柱状图及生态推荐卡。本层对业务逻辑完全透明，仅负责数据呈现。

**【2.3 框架扩展能力设计说明】**

说明架构的可扩展性原理：当用户输入超出10大预置品类范围时，`DynamicAgent`（定义于 `multi_agent.py` 中）通过预训练提示词引导LLM自动生成该品类的核心评价维度，建立临时评分体系，无需任何代码改动。新增预置品类时，开发者只需继承 `BaseProductAgent` → `BaseDbAgent` 并实现 `get_category_config()` 与 `get_specific_dimensions()` 方法，注册至 `MultiCategoryAgent` 路由表即可，体现高内聚低耦合的架构之美。

### 第一节 基于大模型的语义意图识别与参数校准

**【1.1 意图抽取问题的形式化定义】**

将意图识别问题形式化：给定用户原始输入文本 $Q$，目标是通过大语言模型提取关键字段，映射为结构化检索向量（如项目中使用的字典结构）：

$$I = \\{usage,\\ max\\_price,\\ sort\\_field,\\ summary,\\ product\\_type,\\ brand,\\ owned\\_items,\\ budget\\_level\\}$$

使得后续SQLAlchemy查询可以基于 $I$ 直接构造过滤条件，无需任何人工干预。其中 `usage`（用途场景）、`max_price`（最大预算）、`sort_field`（排序维度）、`summary`（核心诉求）为核心四字段；`product_type`（产品子类型，如"头戴式"）、`brand`（目标品牌）、`owned_items`（已购设备列表）、`budget_level`（投入描述）为辅助增强字段。核心挑战有三：歧义消解（"性价比高"的多义性）、预算数值化（"三千左右" → `3000`）、以及缺省字段的合理补全。

**【1.2 基于CoT思维链的Prompt工程设计】**

展示核心意图提取Prompt的设计结构（伪代码形式），说明如何利用JSON Schema约束LLM输出：

```
System Prompt（系统指令）:
  你是一个{品类名}导购专家，负责从对话中提取结构化信息。
  请严格按照以下JSON Schema解析用户输入：
  {
    "usage":        string,  // 使用场景关键词
    "budget_level": string,  // 预算描述
    "max_price":    int,     // 最大预算（元）；未提及则输出 20000
    "sort_field":   string,  // 基于用户需求选择最合适的评分字段
    "summary":      string,  // 解析出的核心诉求
    "product_type": string,  // 目标产品特定类型（如"头戴式"、"游戏本"等）
    "brand":        string,  // 用户明确想要购买的品牌名
    "owned_items":  list     // 用户已经拥有的产品品类或型号
  }

  【推理规则】：
  - 预算缺省默认为 20000。
  - 如果用户提到"不差钱"、"旗舰"、"顶配"，max_price 设为 999999。
  - brand 字段只填用户想买的品牌，已拥有设备的品牌不应填入。

  思维链（CoT）示例：
  用户输入："3000块以内，找个拍vlog好看又轻的相机"
  分析步骤：
    1. 预算提取："3000块以内" → max_price = 3000
    2. 场景识别："拍vlog" → usage = "Vlog拍摄"
    3. 优先维度："好看"对应画质，"轻"对应便携性 → sort_field = "Video_Score"
  输出：{"usage": "Vlog拍摄", "max_price": 3000, "sort_field": "Video_Score",
         "summary": "新手首选", "product_type": "", "brand": "", "owned_items": []}
```

说明CoT设计的两大优势：逐步分析降低提取错误率；JSON Schema硬约束防止LLM输出非结构化文本。

**【1.3 提取结果的三级校验容错机制（配流程图）】**

```
提取结果 I
    │
    ├─ max_price 是否为合法正整数？
    │       否 → 设置默认值 20000（通用预算上限）
    │
    ├─ sort_field 是否在当前品类的合法字段列表中？
    │       否 → 回退至品类默认排序字段（如 Value_Score）
    │
    ├─ 检测极端性能词汇（"最强"、"旗舰"、"不差钱"）？
    │       是 → max_price = 999999，sort_field 映射至品类核心性能维度
    │
    └─ usage 是否非空？
            否 → 以 summary 字段替代，或触发二次追问
```

### 第二节 面向异构商品的参数可量化多维打分

**【2.1 双轴评价维度的抽象设计】**

所有品类的评分体系均由两类维度轴构成：

- **通用评价轴（Universal Dimension）**：跨品类一致的基线维度，在 `BaseProductAgent` 基类中定义为三项：`Value_Score`（性价比，权重0.20）、`Brand_Score`（品牌信誉，权重0.15）、`User_Rating`（用户评价，权重0.15）。
- **专有性能轴（Category-Specific Dimension）**：各品类独有的核心性能维度，例如相机专有 `Portability_Score`（便携性）、`LowLight_Score`（弱光性能）、`Video_Score`（视频能力）；手机专有 `Performance_Score`（性能）、`Battery_Score`（续航）、`Camera_Score`（拍照质量）。

**【2.2 多源异构参数的归一化算法】**

详细推演将原始数据库字段映射至0-100分制的方法，按数据类型分三类处理：

**类型A：布尔型参数（Boolean Mapping）**
```
原始字段：has_ibis（机身防抖）∈ {True, False}
映射规则：True → 100分 | False → 0分
```

**类型B：离散枚举型参数（Tier Mapping）**
```
原始字段：sensor_size ∈ {"1/2.3", "1英寸", "APS-C", "全画幅"}
映射规则（按成像质量分级）：
  "1/2.3"  → 20分
  "1英寸"  → 55分
  "APS-C"  → 80分
  "全画幅" → 100分
```

**类型C：连续数值型参数（Min-Max Normalization with Cap）**
```
原始字段：weight（机身重量，克，越轻越好）
上限截断：weight > 1000 → 视为 1000（异常值处理）
归一化公式：
  score = (1 - (weight - w_min) / (w_max - w_min)) × 100
其中 w_min、w_max 取该品类数据库中的实际极值
```

**【2.3 加权求和与最终得分计算】**

各子项归一化后，通过加权求和得出该维度的最终百分制得分：

$$D_{final} = \sum_{i=1}^{n} w_i \cdot s_i \quad \text{，其中} \sum_{i=1}^{n} w_i = 1.0$$

以相机的 `Video_Score` 为例展示完整加权计算伪代码：

```python
def compute_video_score(camera):
    s1 = 100 if camera.Supports_4K else 0             # 4K支持，权重 0.35
    s2 = sensor_tier_map[camera.Sensor_type]           # 传感器类型，权重 0.30
    s3 = weight_normalize(camera.Weight_g)             # 机身重量，权重 0.20
    s4 = iso_normalize(camera.Max_ISO)                 # 最高ISO，权重 0.15

    return 0.35*s1 + 0.30*s2 + 0.20*s3 + 0.15*s4
```

### 第三节 双层场景化推荐引擎（降级容错机制）

Golden Sets 是由领域专家或品类配置预先定义的优质产品名单。系统中采用关键词加权匹配与场景映射的双重策略：

```python
# 基于 base_agent.py 的场景检测逻辑
def detect_scenario(self, usage, summary):
    # 1. 遍历品类配置中的场景关键词 (scenario_keywords)
    for scenario, keywords in self.config.scenario_keywords.items():
        if any(k in usage for k in keywords) or any(k in summary for k in keywords):
            return scenario
    # 2. 备选方案：场景名称直接匹配
    for scenario in self.config.scenario_presets.keys():
        if scenario in usage or scenario in summary:
            return scenario
    return None

# 获取预设产品列表
def get_preset_products(self, scenario):
    preset_names = self.config.scenario_presets.get(scenario, [])
    # 模糊匹配数据库中的 Model 或 Brand 字段
    return db.query(Model).filter(
        (Model.Model.ilike(f"%{name}%")) | (Model.Brand.ilike(f"%{name}%"))
    ).all()
```

Golden Sets 的核心价值：**将专家经验固化为系统资产，避免LLM每次从头推理带来的发散性和不稳定性**。

从而触发 Fallback。实战中 Fallback 检索不仅考虑价格，还引入了意图解析中的多维约束（品牌、产品类型）：

```sql
-- 实际执行的 Fallback 检索逻辑 (SQLAlchemy 表达)
SELECT * FROM {category_table}
WHERE Price <= {max_price}
  AND Brand LIKE %{brand}%          -- 品牌强过滤 (可选)
  AND (Type LIKE %{product_type}%   -- 耳机类型过滤
    OR Category LIKE %{product_type}%) -- 笔记本分类过滤
ORDER BY {sort_field} DESC
LIMIT 3; -- 默认补齐 3 款
```

**【3.3 兜底去重策略（集合运算）】**

利用集合差集运算保证推荐榜单的新鲜度与非重复性：

```python
def get_ecosystem_by_keywords(user_input: str):
    matched_ecosystems = {}
    user_input_lower = user_input.lower()
    for eco_name, eco_config in ECOSYSTEMS.items():
        score = 0
        # 高权重关键词得分 (10分/个)
        for keyword in eco_config["keywords"]["high"]:
            if keyword in user_input_lower: score += 10
        # 中权重关键词得分 (5分/个)
        for keyword in eco_config["keywords"]["medium"]:
            if keyword in user_input_lower: score += 5
        
        if score > 0: matched_ecosystems[eco_name] = score
    
    # 按分数排序，返回前2个最相关的场景名称列表
    sorted_ecosystems = sorted(matched_ecosystems.items(), key=lambda x: x[1], reverse=True)
    return [name for name, score in sorted_ecosystems[:2]]
```

```python
        ScoringDimension("用户评价", "User_Rating", 0.15, "用户真实反馈评分"),
    ]

    @abstractmethod

    @abstractmethod
    def get_specific_dimensions(self) -> List[ScoringDimension]: ...
    @abstractmethod
    def get_db_session(self): ...
    @abstractmethod
    def get_model_class(self): ...

    def detect_scenario(self, usage: str, summary: str) -> Optional[str]:
```

```python
            ScoringDimension("视频能力", "Video_Score", 0.3, "视频拍摄能力")
        ]

    def handle_chat(self, user_msg, history=None):
```

```python
THEME_COLORS = ['#EC4899', '#8B5CF6', '#D946EF', '#A855F7', '#DB2777']

def draw_radar(products, dimensions=None):
    fig = go.Figure()
    labels = [d[0] for d in dimensions]
    
    for i, p in enumerate(products):
        values = []
        for _, field, max_val in dimensions:
            val = getattr(p, field, 0) or 0
            if max_val:
                val = min(val / max_val * 100, 100)
            values.append(val)
        # 首尾闭合
        values += values[:1]
        color = THEME_COLORS[i % len(THEME_COLORS)]
        
        fig.add_trace(go.Scatterpolar(
            r=values, theta=labels + labels[:1],
            fill='toself', name=p.Model,
            line_color=color, fillcolor=color, opacity=0.2,
            hovertemplate='<b>%{theta}</b>: %{r:.1f}<br>(%{data.name})<extra></extra>'
        ))
    fig.update_layout(
        polar=dict(
            radialaxis=dict(visible=True, range=[0, 100]),
            bgcolor='rgba(255,255,255,0.5)'
        ),
        paper_bgcolor='rgba(0,0,0,0)', plot_bgcolor='rgba(0,0,0,0)'
    )
    return fig
```

## 第七章 总结与展望

### 第一节 本文贡献与总结

本文从电商数码选购场景中用户面临的信息过载、参数壁垒和决策不透明三大痛点出发，设计并实现了一套基于多Agent架构的智能商品选购推荐系统。核心贡献可归纳为三点：

第一，提出了"路由基座 + 品类专家 + 动态扩展"的三级Agent分层架构，实现了10大原生品类的统一管理和未知品类的零配置动态扩展；第二，构建了"LLM意图提取 → 数据库精确检索 → LLM理由生成"的防幻觉闭环，从机制上杜绝了纯LLM推荐系统的核心缺陷；第三，创新性地引入"双联可视化（雷达图+柱状图）+ LLM推荐摘要"的可解释AI交互范式，将黑盒推荐透明化为用户可理解的多维能力图谱，实质性地降低了用户决策门槛。

### 第二节 局限性与项目改进方向

**当前局限性：**

1. 商品数据依赖定期手动爬取更新，暂不支持价格与库存的实时API热拉取，存在数据时效性问题；
2. 系统对强语气词、深层修辞（如讽刺口吻"随便，反正贵的就行"的反向语义）识别精度不足；
3. 评估样本规模较小（n=20），统计显著性有待更大规模用户研究验证。

**未来改进方向：**

1. **RAG知识库增强**：接入检索增强生成（Retrieval-Augmented Generation）技术，将主流KOL深度评测文章作为外挂知识库，增强软性体验维度（手感、噪音等）的评估能力；
2. **实时价格接入**：对接主流电商平台开放API，实现推荐时的实时价格核验与历史价格走势展示；
3. **移动端小程序化**：将系统迁移至微信小程序或React Native，降低用户接入门槛；
4. **多轮对话优化**：引入对话历史感知机制，支持"刚才推荐的第二款，有没有更便宜的替代"式的上下文关联追问。
